# Relational Expense Schema Design

## Scope

Replace the development database's single `expenses` table with normalized
`users`, `categories`, and `expenses` tables. Update the existing expense CRUD
API to use category IDs and a seeded demo user. Authentication and category
management endpoints remain outside this change.

The existing development data is disposable. Replace the initial migration and
rebuild the database rather than preserving or backfilling rows.

## Tables

All IDs are UUIDs generated by the application. All timestamps are PostgreSQL
`TIMESTAMPTZ` values with `now()` defaults.

### users

- `id`: UUID primary key
- `email`: required text, unique
- `name`: required text
- `default_currency`: required three-character text, default `EUR`
- `created_at`: required timestamp

### categories

- `id`: UUID primary key
- `user_id`: required foreign key to `users.id`, cascading on user deletion
- `name`: required text
- `icon`: nullable text
- unique constraint on `(user_id, name)`
- supporting index on `user_id`

### expenses

- `id`: UUID primary key
- `user_id`: required foreign key to `users.id`, cascading on user deletion
- `merchant`: nullable text
- `description`: nullable text
- `amount`: required `NUMERIC(12,2)` with a positive-value check
- `currency`: required three-character text
- `category_id`: required UUID
- `spent_at`: required date
- `created_at`: required timestamp
- `updated_at`: required timestamp
- composite foreign key `(category_id, user_id)` to
  `categories(id, user_id)`, restricting category deletion while referenced
- indexes on `(user_id, spent_at)` and `category_id`

The composite category foreign key prevents an expense from using a category
owned by another user. `categories` therefore has a supporting unique
constraint on `(id, user_id)`.

## Seed Data

The initial migration inserts one fixed demo user with EUR as the default
currency and these categories:

- groceries
- restaurants
- transport
- rent
- utilities
- shopping
- entertainment
- health
- travel
- subscriptions
- other

Stable UUIDs make the seeded user and categories usable by the API and tests.
The migration owns its literal seed values so later application refactors do
not change migration history.

## Application Changes

`User`, `Category`, and `Expense` SQLAlchemy models mirror the database
constraints. No ORM relationships are added because current queries only need
foreign-key IDs.

Expense create, update, and response schemas use `category_id: UUID` instead
of a category name. Routes continue to use the internal demo user UUID and do
not accept `user_id` from clients.

Before creating or changing an expense's category, the service verifies that
the category exists for the demo user. A missing or foreign category produces
HTTP `404`. All expense reads and mutations remain scoped by user ID.

## Migration and Reset

Replace the existing initial migration with the complete schema and seed data.
Recreate the disposable PostgreSQL volume, then run `alembic upgrade head`.
Do not add a second migration that immediately discards the first schema.

## Testing

API tests create the three-table schema in temporary SQLite, insert the fixed
demo user and categories, and cover:

- create, list, read, update, and delete using `category_id`
- positive decimal validation and empty PATCH rejection
- default currency and timestamps
- rejection of a category owned by another user
- database constraints for user/category ownership

Run pytest, Ruff, Alembic migration upgrade, and `alembic check` before
completion.

## Deferred

- Authentication will replace the fixed demo user context.
- Category CRUD will replace migration-only category provisioning.
- Case-insensitive email handling belongs with user registration.
